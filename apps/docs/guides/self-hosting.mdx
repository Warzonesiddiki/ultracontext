You can self-host the Context API instead of using the managed service at ultracontext.ai.

## Prerequisites

- **Node.js >= 22**
- **PostgreSQL** (direct or via Supabase)
- **Docker** (optional, for local Postgres)

## Quick start with Docker

The monorepo includes a Docker Compose setup for local PostgreSQL:

<CodeGroup>
```bash npm
git clone https://github.com/ultracontext/ultracontext.git
cd ultracontext

# start PostgreSQL
npm run ultracontext:db:up

# apply schema
npm run ultracontext:db:migrate

# start the API
npm run ultracontext:api
```

## Database schema

Create these tables in your PostgreSQL database:

```sql SQL
create table projects (
  id bigserial primary key,
  name text not null,
  created_at timestamptz not null default now(),
  public_id text
);

create table api_keys (
  id bigserial primary key,
  project_id bigint not null,
  key_prefix text not null,
  key_hash text not null,
  name text,
  last_used_at timestamptz,
  created_at timestamptz not null default now()
);

create table nodes (
  id bigserial primary key,
  public_id text not null,
  project_id bigint not null,
  type text not null,
  content jsonb not null default '{}'::jsonb,
  metadata jsonb not null default '{}'::jsonb,
  created_at timestamptz not null default now(),
  parent_id text,
  prev_id text,
  context_id text,
  -- position within the context_id partition; see "Health and chain integrity"
  ordinal bigint
);

-- named branches: a name pinned to an immutable version head id
create table context_refs (
  id bigserial primary key,
  project_id bigint not null,
  context_id text not null,
  name text not null,
  head_id text not null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create unique index if not exists uq_context_refs_project_context_name
  on context_refs (project_id, context_id, name);

-- GIN index for fast metadata filtering
create index if not exists idx_nodes_metadata
  on nodes using gin (metadata);

-- chain ordering: MAX(ordinal) per partition on write, ordered reads on the
-- fallback path
create index if not exists idx_nodes_context_ordinal
  on nodes (context_id, ordinal);
```

<Note>
  This sketch is here to explain the shape of the data, not to be your install
  script. The canonical schema is **`apps/postgres/init.sql`**, generated from
  the migration registry in `packages/storage/src/migrations/` — run that file
  instead of copying DDL by hand, so your database carries every column the API
  selects (`ordinal`, `context_refs`) and stamps the migration versions it
  contains. Direct PostgreSQL and Drizzle clients also auto-migrate on connect.
</Note>

## Storage adapters

The Context API uses a **storage adapter pattern** to abstract database operations. You can choose between two backends:

- **Direct PostgreSQL** — Drizzle ORM with a direct connection
- **Supabase** — Supabase REST client for managed PostgreSQL

Both produce identical API behavior.

| | Direct PostgreSQL | Supabase |
|---|---|---|
| **Best for** | Self-hosted, full control | Managed hosting, quick setup |
| **Connection** | Direct TCP | REST API (HTTPS) |
| **Latency** | Lower | Slightly higher (HTTP overhead) |
| **Setup** | Manage your own PostgreSQL | Create a Supabase project |
| **Scaling** | Manual | Handled by Supabase |
| **Atomic permanent delete** | Yes (real transactions) | Best-effort (sequential REST) |
| **Append-vs-delete race safety** | Yes (SERIALIZABLE isolation) | Best-effort (no isolation) |
| **Open source** | Yes | Yes |

### Direct PostgreSQL

```bash .env
DATABASE_PROVIDER=postgres
DATABASE_URL=postgresql://user:password@host:5432/ultracontext
ULTRACONTEXT_ADMIN_KEY=your_admin_key
```

Best for self-hosted deployments where you manage your own database. Lower latency via direct TCP connection.

### Supabase

```bash .env
DATABASE_PROVIDER=supabase
SUPABASE_URL=https://your-project.supabase.co
SUPABASE_SERVICE_ROLE_KEY=eyJhbGci...
ULTRACONTEXT_ADMIN_KEY=your_admin_key
```

Best for managed hosting and quick setup. Scaling handled by Supabase.

<Note>Permanent delete operations (`uc.delete(..., {permanent: true})` and `uc.deleteMany(...)`) run as sequential REST calls on this provider — a mid-operation failure may leave partially-deleted state. Use the `postgres` provider for atomic permanent delete.</Note>

<Warning>Use the **service role key**, not the anon key. The service role key bypasses Row Level Security, which the API needs to manage data across projects.</Warning>

<Steps>
  <Step title="Create a Supabase project">
    Go to [supabase.com](https://supabase.com) and create a new project.
  </Step>
  <Step title="Create the tables">
    Run the SQL schema above in the Supabase SQL editor.
  </Step>
  <Step title="Get your credentials">
    In your Supabase dashboard, go to **Settings > API**. Copy:
    - **Project URL** — your `SUPABASE_URL`
    - **service_role key** — your `SUPABASE_SERVICE_ROLE_KEY`
  </Step>
  <Step title="Set environment variables">
    Add the Supabase env vars shown above to your `.env` file.
  </Step>
</Steps>

## Environment variables

| Variable | Required | Description |
|---|---|---|
| `DATABASE_PROVIDER` | Yes | Storage provider: `postgres` or `supabase` |
| `DATABASE_URL` | If using PostgreSQL | PostgreSQL connection string |
| `SUPABASE_URL` | If using Supabase | Supabase project URL |
| `SUPABASE_SERVICE_ROLE_KEY` | If using Supabase | Supabase service role key |
| `ULTRACONTEXT_ADMIN_KEY` | Yes | Admin key for key management endpoints |
| `PORT` | No | API server port (default: 8787) |

## Deploy to Cloudflare Workers

The Context API ships with a Workers entrypoint (`src/worker.ts`) that runs on Cloudflare's edge network. Only the **Supabase** storage adapter is supported on Workers (no direct TCP to PostgreSQL).

### Prerequisites

- A [Supabase](https://supabase.com) project with the schema applied
- [Wrangler CLI](https://developers.cloudflare.com/workers/wrangler/) installed

### Configure

Create a `wrangler.jsonc` in `apps/api`:

```jsonc wrangler.jsonc
{
    "name": "ultracontext-api",
    "main": "src/worker.ts",
    "compatibility_date": "2024-12-01"
}
```

Set your secrets via `wrangler secret put`:

```bash
wrangler secret put DATABASE_PROVIDER        # enter: supabase
wrangler secret put SUPABASE_URL
wrangler secret put SUPABASE_SERVICE_ROLE_KEY
wrangler secret put ULTRACONTEXT_ADMIN_KEY
```

### Optional: API key caching with KV

You can cache API key lookups using Workers KV to reduce Supabase calls:

1. Create a KV namespace: `wrangler kv namespace create ULTRACONTEXT_API_KEYS_CACHE`
2. Add the binding to `wrangler.jsonc`:

```jsonc wrangler.jsonc
{
    "kv_namespaces": [
        {
            "binding": "ULTRACONTEXT_API_KEYS_CACHE",
            "id": "<your-namespace-id>"
        }
    ]
}
```

When the binding is present, key lookups are cached for 1 hour. Without it, every request queries Supabase directly (same behavior as Node.js).

### Deploy

```bash
cd apps/api && npx wrangler deploy
```

## Health and chain integrity

Two unauthenticated probes are served for load balancers and orchestrators,
which cannot hold API keys:

| Endpoint | Meaning |
|---|---|
| `GET /health` | Liveness: the process is up and serving. Also carries the chain-health counters below. |
| `GET /health/ready` | Readiness: the storage backend answered a trivial read. 503 when it did not. |

Message order inside a version is a linked list — each node points at its
predecessor through `prev_id`. When a read cannot walk that list (a database
damaged by an older crash, a hand edit, a partial import), ordering falls back
to the persisted `ordinal`, then `created_at`, then the unique public id, so the
result stays deterministic instead of depending on the order rows came back in.
Every fallback is counted:

```json
{
  "status": "ok",
  "chain_health": {
    "fallbacks": 0,
    "nodes_lost": 0,
    "contexts_affected": 0,
    "last_fallback_at": null
  }
}
```

Alert on `chain_health.fallbacks > 0`. Note what does **not** happen:

- `status` stays `"ok"`. A damaged chain is data, not a dead process — a
  liveness probe that failed on it would restart a healthy server and fix
  nothing.
- Nothing is sent anywhere. The counters live in the API process, reset when it
  restarts, and are only ever read by you. UltraContext has no telemetry.
- The affected context id is not in the response, because this endpoint is
  unauthenticated. It is in the server log line, prefixed
  `[ultracontext:chain-health]`, together with the same numbers as JSON.

## MCP endpoint

Self-hosted APIs include a built-in MCP endpoint at `/mcp`. No extra setup needed -- it uses the same Bearer token authentication as the REST API. See [MCP Server](/fundamentals/mcp-server#remote-mode-http) for details.
